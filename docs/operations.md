# Эксплуатация

## Минимальная схема

Интернет → Nginx/HTTPS → Gunicorn/Django → PostgreSQL. Отдельный процесс того же приложения `deliver_pending --loop` читает оплаченные недоставленные заказы. Private PDF и публичные изображения — разные каталоги/volumes. Настроенный HTTPS обязателен для production; в коде уже включены secure cookies, HSTS и CSP.

Docker Compose локально слушает только 127.0.0.1:8000. Для VPS оставьте это ограничение; публичные 80/443 обслуживает Nginx. PostgreSQL наружу не открывается. Образ работает от uid 10001. Миграции и collectstatic выполняет одноразовый init, его ошибка блокирует web/delivery.

## Размещение файла

```bash
docker compose cp /ABSOLUTE/PATH/cookbook.pdf web:/app/private/cookbook.pdf
```

Убедитесь, что uid 10001 может читать файл (например, chmod 640 с нужной группой внутри контейнера). Volume общий для web и worker. В Admin задайте только `cookbook.pdf`, без пути. Новая версия продукта может использовать новое имя файла; не удаляйте книгу, пока есть действующие покупки. Приложение намеренно не отдаёт private/ через Nginx или Django static.

Для публичных изображений Admin использует `/app/public-media`. На VPS настройте bind mount этой директории к `/srv/recipe-shop/public-media` для Nginx либо используйте отдельное публичное объектное хранилище и соответствующий storage backend. Не используйте volume PDF в public alias. В текущем Compose публичные images в named volume: точку монтирования можно узнать через `docker volume inspect`, затем организовать read-only bind к Nginx. Публичные файлы загружают только доверенные staff; расширения ограничены JPEG/PNG/WebP, SVG/HTML не разрешены.

## Проверки перед запуском

```bash
docker compose config --quiet
docker compose run --rm web python manage.py check --deploy
docker compose run --rm web python manage.py check_launch
docker compose exec web python manage.py test tests --settings=config.postgres_settings
```

Не публикуйте полный `docker compose config`: он может раскрывать env-секреты. `check_launch` намеренно завершается ошибкой для демоматериалов, draft legal, незаполненной идентичности, тестового терминала/DEBUG/тестового режима Robokassa/console mail и отсутствующего PDF. Это проверка наличия настроек, не проверка договора, налогов или фактического зачисления денег.

Не используйте созданные для CI/локального теста ключи/роли на production. Приложению достаточно обычной роли БД, для миграций нужны права изменения схемы; CREATEDB требуется только тестовой роли. Выделите тестовую БД отдельно.

## Наблюдение

- `/health/` проверяет доступ к БД, не открывает секреты. Политика перенаправления допускает HTTP только для этого локального health endpoint.
- Worker обновляет `/tmp/delivery-heartbeat`; Compose health check замечает зависание/остановку. Не интерпретируйте health web как успешную отправку email.
- Следите за `delivery_status=failed`, `delivery_attempts>=8`, длительно pending заказами и отклонениями webhook. Сверяйте деньги с кабинетом провайдера.
- Внутренние логи содержат короткие коды и UUID, не email, ключи или payload. Django server access log отключён на INFO, Nginx access log выключен, Gunicorn access log не включён. Не подключайте внешнюю аналитику с записью download URL. Логи ошибок proxy/бэкапов храните с ограниченным доступом.
- Если SMTP принял сообщение, а получатель не получил его, проверяйте bounce/логи у SMTP-провайдера и адрес. Приложение не реализует callback доставки/bounce и не утверждает, что письмо попало во входящие.

## Обновления и резервные копии

Остановите приём новых покупок (`SALES_ENABLED=False`), сделайте backup, обновите исходники/образ, выполните миграции, `check --deploy`, `check_launch` и smoke test. Для схем с несовместимыми изменениями согласуйте окно обслуживания. Перед выкладкой фиксируйте и обновляйте версии зависимостей в соответствии с политикой проекта; `requirements-tested.txt` перечисляет фактически использованные версии проверки Windows.

Для backup PostgreSQL используйте `pg_dump -Fc` внутри db-контейнера, перенаправляя бинарный вывод в файл через подходящую оболочку Linux (старый PowerShell может испортить бинарный stdout). Пример на Linux:

```bash
mkdir -p /srv/backups/cookbook
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > /srv/backups/cookbook/database.dump
```

Отдельно копируйте private_files, public_images, `.env`/секреты в защищённое хранилище. Шифруйте и отправляйте копии вне VPS, ограничивайте доступ, задайте срок хранения, регулярно восстанавливайте в изолированную БД и проверяйте оплату/выдачу. Не храните резервные копии в public static/media.

Старые счётчики лимитов можно периодически удалять по `RateBucket.start` старше суток через Django ORM. Срок хранения email/заказов должен быть определён продавцом в политике с учётом обязательных учётных требований. Не удаляйте платёжный журнал вслепую: он обеспечивает дедупликацию событий.

## Ограничения

Нет повторного списания, подписок, гостевого публичного resend endpoint или самостоятельного возврата. Это уменьшает риск злоупотреблений. Покупатель обращается в поддержку; администратор сверяет оплаченный заказ и отправляет ссылку повторно. Автоматическая сверка потерянных webhook не реализована: провайдер повторяет доставку, длительные pending сверяются оператором. SMTP и БД не имеют общей транзакции, редкое повторное письмо после аварии возможно.

Фискализация/Робочеки или собственная касса с конкретными налоговыми параметрами, сквозная обработка кассовых событий, юридическая экспертиза и production-инфраструктура остаются обязанностью активации владельцем; `FISCALIZATION_READY` не заменяет их.


При миграции на Robokassa не сбрасывайте БД и InvId sequence. Сначала backup и сверка pending прежнего провайдера; затем migrate и настройка Result/Success/Fail согласно docs/payment.md.
